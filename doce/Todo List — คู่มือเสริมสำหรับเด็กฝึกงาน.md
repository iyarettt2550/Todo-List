## อภิธานศัพท์

คำที่จะเจอบ่อยในโปรเจกต์นี้ ไม่ต้องจำทั้งหมดก่อนเริ่ม ให้กลับมาเปิดดูเมื่อเจอคำที่ไม่รู้

### ภาพรวมระบบ

| คำ | ความหมาย | ในโปรเจกต์นี้ |
| --- | --- | --- |
| หน้าบ้าน (Frontend / Client) | ส่วนที่ผู้ใช้เห็นและกดได้ ทำงานในเบราว์เซอร์ | โฟลเดอร์ `client` (React) |
| หลังบ้าน (Backend / Server) | โปรแกรมที่รับคำขอจากหน้าบ้าน แล้วไปอ่านหรือเขียนฐานข้อมูล | โฟลเดอร์ `server` (Express) |
| ฐานข้อมูล (Database / DB) | ที่เก็บข้อมูลถาวร ปิดเครื่องแล้วข้อมูลก็ไม่หาย | PostgreSQL |
| API | ช่องทางที่โปรแกรมสองตัวคุยกัน ตกลงกันไว้ว่าส่งอะไรแล้วจะได้อะไรกลับ | หน้าบ้านคุยกับหลังบ้านผ่าน `/api/...` |
| CRUD | 4 งานพื้นฐานกับข้อมูล: Create สร้าง, Read อ่าน, Update แก้, Delete ลบ | เพิ่ม ดู ติ๊ก ลบงาน |

### การคุยกันผ่าน HTTP

| คำ | ความหมาย | ในโปรเจกต์นี้ |
| --- | --- | --- |
| Request / Response | คำขอที่ส่งไป และคำตอบที่ได้กลับมา | หน้าบ้านส่ง request แล้วหลังบ้านตอบ response |
| Endpoint | ที่อยู่ของ API แต่ละตัว คือ method + path | `POST /api/todos` |
| HTTP method | บอกว่าจะทำอะไรกับข้อมูล | GET อ่าน, POST สร้าง, PATCH แก้, DELETE ลบ |
| Status code | ตัวเลขบอกผลลัพธ์ 2xx สำเร็จ, 4xx ผู้ส่งส่งผิด, 5xx เซิร์ฟเวอร์พัง | 200, 201, 204, 400, 404, 500 |
| JSON | รูปแบบข้อความที่ใช้ส่งข้อมูล หน้าตาคล้าย object ใน JS | `{ "title": "ซื้อกาแฟ" }` |
| REST | แนวทางออกแบบ API ให้ใช้ path แทนสิ่งของ และใช้ method แทนการกระทำ | `/api/todos/4` คืองานหมายเลข 4 |
| Proxy | ตัวกลางที่ส่งต่อคำขอไปอีกที่ | Vite ส่งต่อ `/api` ไปพอร์ต 3000 |
| CORS | กฎของเบราว์เซอร์ที่ห้ามเว็บเรียกข้ามโดเมนหรือพอร์ตโดยไม่ได้รับอนุญาต | เลี่ยงได้ด้วย proxy |

### ฝั่งหลังบ้านและฐานข้อมูล

| คำ | ความหมาย | ในโปรเจกต์นี้ |
| --- | --- | --- |
| ตาราง / แถว / คอลัมน์ | ตารางคือชุดข้อมูลประเภทเดียวกัน แถวคือข้อมูล 1 ชิ้น คอลัมน์คือช่องข้อมูล | ตาราง `todos` มีคอลัมน์ `title`, `done` |
| Primary key | คอลัมน์ที่ไม่ซ้ำกันเลย ใช้ระบุแถว | `id` |
| Schema | โครงสร้างที่บอกว่ามีตารางอะไร คอลัมน์อะไร type อะไร | `schema.prisma` |
| ORM | ไลบรารีที่ให้เขียนโค้ดแทน SQL แล้วแปลงเป็น SQL ให้ | Prisma, `prisma.todo.findMany()` |
| Migration | ไฟล์บันทึกการเปลี่ยนโครงสร้าง DB ทีละครั้ง ใช้สร้าง DB ให้เหมือนกันทุกเครื่อง | `npx prisma migrate dev` |
| Seed | ใส่ข้อมูลตัวอย่างลง DB | `prisma/seed.ts` |
| Validation | ตรวจว่าข้อมูลที่ส่งมาถูกต้องก่อนนำไปใช้ | Zod |
| Middleware | ฟังก์ชันที่ทุก request วิ่งผ่านก่อนหรือหลัง route | `express.json()`, `errorHandler` |
| Environment variable (.env) | ค่าที่ต่างกันในแต่ละเครื่อง เช่น รหัสผ่าน DB แยกไว้นอกโค้ดและห้าม commit | `DATABASE_URL` |

### TypeScript และ Git

| คำ | ความหมาย | ในโปรเจกต์นี้ |
| --- | --- | --- |
| Type | บอกว่าตัวแปรเก็บข้อมูลแบบไหน ช่วยจับข้อผิดพลาดก่อนรัน | `type Todo = { id: number; ... }` |

## แผนรายวัน

โปรเจกต์นี้ใช้เวลา 5 วันทำงาน ถ้าทำเสร็จก่อนให้ไปต่อที่หัวข้อ "ต่อยอด" ใน Spec ส่วนถ้าเลยวันไหนเกินครึ่งวัน ให้บอกพี่เลี้ยงทันที ไม่ต้องรอจนถึงวันส่ง

| วัน | Task ในเอกสารสอน | เย็นนี้ต้องได้ |
| --- | --- | --- |
| 1 | Task 0–2 | server ตอบ `/api/health` และมีตาราง `todos` ใน DB พร้อมข้อมูล 3 แถว |
| 2 | Task 3–5 | API ครบ 4 ตัว และผ่าน checklist หลังบ้านใน Spec |
| 3 | Task 6–8 | หน้าเว็บแสดงรายการจาก DB และเพิ่มงานได้ |
| 4 | Task 9–10 | ติ๊ก ลบ ฟิลเตอร์ และตัวนับทำงานครบ |
| 5 | เก็บงาน | ผ่าน checklist ทั้งหมด มี README และ demo ให้พี่เลี้ยงดู |

### ทุกวัน

- **เช้า (10 นาที):** คุยสั้นๆ ทุกคน ตอบ 3 ข้อ เมื่อวานทำอะไรเสร็จ วันนี้จะทำอะไร และติดอะไรอยู่
- **ระหว่างวัน:** ทำ Task ไหนผ่าน checklist แล้วให้เปิด PR ทันที ไม่ต้องรอรวมหลาย Task
- **ก่อนเลิกงาน:** push งานที่ทำอยู่ขึ้น branch ทุกครั้ง ถึงจะยังไม่เสร็จก็ตาม

### Demo วันที่ 5 (10 นาทีต่อคน)

1. เปิดเว็บแล้วทำให้ดูครบ: เพิ่ม → ติ๊ก → ฟิลเตอร์ → ลบ → รีเฟรช
2. ปิด server แล้วโชว์ว่าหน้าเว็บแสดง error ไม่ใช่จอขาว
3. เปิดโค้ด 1 ไฟล์ที่ภูมิใจที่สุด แล้วอธิบายว่าทำงานอย่างไร
4. เล่าปัญหาที่ยากที่สุดที่เจอ และแก้อย่างไร

## วิธีรันโปรเจกต์

### .env.example

ไฟล์ `.env` ห้าม commit เพราะมีรหัสผ่าน แต่คนอื่นต้องรู้ว่าต้องมีค่าอะไรบ้าง จึงทำไฟล์ตัวอย่างไว้ใน repo แทน

```bash
# server/.env.example — คัดลอกเป็น .env แล้วแก้ user/password ให้ตรงเครื่องตัวเอง
DATABASE_URL="postgresql://postgres:secret@localhost:5432/todo_app?schema=public"
```

เพิ่ม script ใน `server/package.json` เพื่อให้จำคำสั่งน้อยลง

```json
{
  "scripts": {
    "dev": "tsx watch src/index.ts",
    "typecheck": "tsc --noEmit",
    "db:migrate": "prisma migrate dev",
    "db:seed": "tsx prisma/seed.ts",
    "db:studio": "prisma studio"
  }
}
```

### รันครั้งแรก (หลัง clone repo)

เปิด PostgreSQL ให้เรียบร้อยก่อน แล้วใช้ 2 terminal

```bash
# terminal 1: หลังบ้าน
cd server
cp .env.example .env      # แล้วแก้รหัสผ่านใน .env
npm install
npm run db:migrate
npm run db:seed
npm run dev
```

```bash
# terminal 2: หน้าบ้าน
cd client
npm install
npm run dev
```

จากนั้นเปิด `http://localhost:5173`

### รันวันต่อๆ ไป

เปิด PostgreSQL แล้วรัน `npm run dev` ในทั้งสองโฟลเดอร์ ถ้า pull โค้ดใหม่มาแล้วมี migration เพิ่ม ให้รัน `npm run db:migrate` ก่อน

### ล้าง DB เริ่มใหม่

```bash
cd server
npx prisma migrate reset   # ลบข้อมูลทั้งหมดแล้วสร้างตารางใหม่ ระวังใช้กับ DB จริง
npm run db:seed
```

## การส่งงานด้วย Git

แต่ละคนทำ repo ของตัวเอง แต่รีวิวงานกันแบบทีม คือพี่เลี้ยงรีวิว และเพื่อนอีก 1 คนช่วยรีวิวด้วย ใช้ได้ทั้ง GitHub และ GitLab ขั้นตอนเหมือนกัน

### กติกา

- ห้าม push ตรงเข้า `main` ต้องผ่าน PR/MR ทุกครั้ง
- 1 Task = 1 branch = 1 PR/MR
- ห้าม commit `.env`, `node_modules` และ `dist` ให้ใส่ไว้ใน `.gitignore` ตั้งแต่ commit แรก

### ขั้นตอนส่ง 1 Task

```bash
# 1. เริ่มจาก main ล่าสุด
git checkout main
git pull

# 2. แตก branch ตามชื่อ Task
git checkout -b task/04-get-post-api

# 3. ทำงาน แล้ว commit เป็นระยะ
git add .
git commit -m "feat: add GET /api/todos"

# 4. push แล้วเปิด PR/MR บนเว็บ
git push -u origin task/04-get-post-api
```

5. ใส่ reviewer เป็นพี่เลี้ยงกับเพื่อน 1 คน
6. ถ้ามีคอมเมนต์ ให้แก้แล้ว commit และ push เพิ่มใน branch เดิม ไม่ต้องเปิด PR ใหม่
7. เมื่อได้ approve แล้วให้กด merge แล้วลบ branch จากนั้นกลับไปข้อ 1

### ชื่อ branch และ commit

ชื่อ branch ใช้รูปแบบ `task/<เลข 2 หลัก>-<สิ่งที่ทำ>` เช่น `task/07-show-list`

ข้อความ commit ให้ขึ้นต้นด้วยประเภท แล้วตามด้วยสิ่งที่ทำ เป็นภาษาอังกฤษสั้นๆ

| ประเภท | ใช้เมื่อ | ตัวอย่าง |
| --- | --- | --- |
| `feat` | เพิ่มความสามารถใหม่ | `feat: add delete button` |
| `fix` | แก้บั๊ก | `fix: return 404 when todo not found` |
| `refactor` | ปรับโค้ดโดยผลลัพธ์ไม่เปลี่ยน | `refactor: move fetch calls to api.ts` |
| `docs` | แก้เอกสาร | `docs: add setup steps to README` |
| `chore` | งานจุกจิก เช่น config หรือ dependency | `chore: add prisma scripts` |

### Template คำอธิบาย PR/MR

```markdown
## ทำอะไร
Task 4: GET และ POST /api/todos

## ทดสอบยังไง
- [ ] ผ่านทุกข้อใน "เช็คว่าผ่าน" ของ Task นี้
- [ ] npm run typecheck ผ่าน

## ภาพหน้าจอ / ผลจาก curl
(แปะตรงนี้)

## สิ่งที่ยังไม่แน่ใจ
(ถ้าไม่มีให้เขียนว่า "ไม่มี")
```

### ตอนรีวิวงานเพื่อน

- ลอง pull branch ของเพื่อนมารันจริง ไม่ใช่แค่อ่านโค้ด
- คอมเมนต์ที่โค้ด ไม่ใช่ที่ตัวคน เช่น "ตรงนี้ถ้า id ไม่ใช่ตัวเลขจะเป็นยังไง" ไม่ใช่ "เขียนผิดอีกแล้ว"
- ถ้าไม่เข้าใจตรงไหนให้ถาม ได้ฝึกทั้งคนถามและคนตอบ

### ข้อควรระวัง

- คัดลอกโค้ดและ error มาเป็นข้อความ ไม่ใช่แคปหน้าจอ คนช่วยจะคัดลอกไปลองต่อได้
- ห้ามส่งไฟล์ `.env` หรือรหัสผ่านให้ AI หรือแปะในแชทกลุ่ม
- ถ้า AI ให้โค้ดมา ต้องอธิบายได้ว่าแต่ละบรรทัดทำอะไรก่อนจะใช้ เพราะตอน demo จะถูกถาม
- เมื่อแก้ได้แล้ว ให้กลับไปบอกในเธรดเดิมว่าแก้ยังไง เพื่อนที่ติดแบบเดียวกันจะได้ไม่ต้องถามซ้ำ

## เกณฑ์ประเมิน

พี่เลี้ยงจะประเมินหลัง demo วันที่ 5 คะแนนนี้ใช้ดูว่าแต่ละคนพร้อมแค่ไหน และควรได้งานส่วนไหนในโปรเจกต์จริง ไม่ได้ใช้ลงโทษ แต่ละหัวข้อให้ 1–3 คะแนน แล้วคูณกับน้ำหนัก

| หัวข้อ | น้ำหนัก | 3 = ดี | 2 = พอใช้ | 1 = ต้องปรับ |
| --- | --- | --- | --- | --- |
| ระบบทำงานครบ | 30% | ผ่าน checklist ทุกข้อ | ขาดไม่เกิน 3 ข้อ | ขาดเกิน 3 ข้อ |
| คุณภาพโค้ด | 20% | อ่านง่าย ตั้งชื่อดี type ครบ ไม่มี `any` | อ่านได้ แต่มีจุดซ้ำหรือชื่อไม่สื่อ | อ่านยาก หรือมี `any` |
| การจัดการ error | 15% | ไม่มี 500 จาก input ผิด และหน้าบ้านแสดง error ครบทุกสถานะ | ครบบางส่วน | ระบบพังเมื่อ input ผิด หรือขึ้นจอขาว |
| Git และ PR/MR | 15% | 1 Task = 1 PR, commit สื่อความหมาย, แก้ตามรีวิวครบ | ทำตามบ้าง | push ตรงเข้า main หรือ commit ก้อนเดียว |
| การสื่อสาร | 10% | ถามตาม template แจ้งเมื่อจะช้า และช่วยรีวิวงานเพื่อน | ถามได้แต่ข้อมูลไม่ครบ | ติดเงียบ หรือถามโดยไม่ลองก่อน |
| ความเข้าใจ | 10% | อธิบายโค้ดตัวเองได้ทุกจุดตอน demo | อธิบายได้บางส่วน | อธิบายโค้ดที่ตัวเองส่งมาไม่ได้ |

### 4. เทส API อัตโนมัติ

**ทำไม:** ตอนนี้เราเทสด้วยการยิง curl ทีละคำสั่ง แก้โค้ดครั้งหนึ่งก็ต้องยิงใหม่ทั้งหมด ถ้าเขียนเป็นเทสไว้ สั่งคำสั่งเดียวก็ตรวจครบทุกข้อ

```bash
cd server
npm i -D vitest supertest @types/supertest
```

แยกการสร้างแอปออกจาก `listen` ก่อน เพื่อให้เทสเรียกใช้แอปได้โดยไม่ต้องเปิดพอร์ตจริง

```ts
// server/src/app.ts
import express from "express";
import { todosRouter } from "./routes/todos";
import { errorHandler } from "./errors";

export const app = express();
app.use(express.json());
app.get("/api/health", (_req, res) => {
  res.json({ ok: true });
});
app.use("/api/todos", todosRouter);
app.use(errorHandler);
```

```ts
// server/src/index.ts
import { app } from "./app";

app.listen(3000, () => console.log("API on http://localhost:3000"));
```

```ts
// server/src/todos.test.ts
import request from "supertest";
import { describe, expect, it } from "vitest";
import { app } from "./app";

describe("POST /api/todos", () => {
  it("returns 400 when title is blank", async () => {
    const res = await request(app).post("/api/todos").send({ title: "   " });
    expect(res.status).toBe(400);
  });

  it("returns 201 with the new todo", async () => {
    const res = await request(app).post("/api/todos").send({ title: "from test" });
    expect(res.status).toBe(201);
    expect(res.body).toMatchObject({ title: "from test", done: false });
  });
});

describe("PATCH /api/todos/:id", () => {
  it("returns 404 for unknown id", async () => {
    const res = await request(app).patch("/api/todos/999999").send({ done: true });
    expect(res.status).toBe(404);
  });
});
```

เพิ่ม `"test": "vitest"` ใน scripts แล้วรัน `npm test`

**โจทย์:** เขียนเทสให้ครอบคลุมทุกข้อใน checklist หลังบ้านของ Spec

**ระวัง:** เทสชุดนี้เขียนลง DB จริง ถ้าอยากทำให้ถูกต้องควรใช้ DB แยกสำหรับเทส เช่น `todo_app_test` ผ่านไฟล์ `.env.test` ให้ลองถาม AI หรือพี่เลี้ยงเรื่องนี้เป็นโจทย์ต่อ

### 5. คอลัมน์ updated\_at

**ทำไม:** แทบทุกตารางในงานจริงเก็บเวลาที่แก้ไขล่าสุด ใช้เรียงข้อมูล หาว่าอะไรเพิ่งเปลี่ยน หรือตรวจย้อนหลัง

```prisma
// server/prisma/schema.prisma (เพิ่มใน model Todo)
updatedAt DateTime @updatedAt @map("updated_at") // Prisma อัปเดตให้อัตโนมัติทุกครั้งที่ update
```

```bash
npx prisma migrate dev --name add_updated_at
```

จากนั้นเพิ่ม `updatedAt: string` ใน `type Todo` ฝั่ง client

**เช็คว่าผ่าน:**

- [ ] งานที่มีอยู่แล้วมีค่า `updatedAt`
- [ ] ติ๊กเสร็จแล้ว `updatedAt` เปลี่ยน แต่ `createdAt` ไม่เปลี่ยน
- [ ] แสดงบนหน้าเว็บว่า "แก้ไขล่าสุดเมื่อ ..." เป็นเวลาไทย (ใช้ `toLocaleString("th-TH")`)
